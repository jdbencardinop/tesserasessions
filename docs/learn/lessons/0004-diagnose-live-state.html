Lesson 4 of 4

Separate presence from state

Ask whether a runtime exists and what its agent is doing as two different questions.

Course index Mission Glossary Runbook Lesson 4

OutcomeInterpret live evidence without inventing certainty.

TimeAbout 10 minutes.

Two axes prevent one overloaded status

runtime_presence answers whether a matching live runtime was observed. agent_state answers what the observed agent is doing. Neither axis replaces local topology, failures, locks, or final dashboard rollup.

Presence Agent state Meaning
present working A matching live agent is active.
present ready A matching live agent can accept input.
present blocked A matching live agent needs attention.
absent unknown No matching live runtime was observed.
stale unknown Runtime evidence exists but is outside its freshness window.
unknown unknown Coverage or match evidence is insufficient.

Ready is not idle. Ready requires a live agent. Idle is a normalized inventory/dashboard concept for work not currently active.

Practice: issue one side-effect-free query

Side-effect-free This command does not scan, write the inventory, attach, focus, or send input. 

printf '%s\n' '{
  "schema_version": 1,
  "queries": [{
    "query_id": "demo-api",
    "path": "/workspaces/demo-api",
    "repo_root": "/repos/demo",
    "git_branch": "feature/demo"
  }]
}' | tss status --json

Read the response from the outside in:

  1. Confirm schema_version and freshness timestamps.
  2. Check provider availability and provider-level errors.
  3. Find your opaque query_id.
  4. Interpret presence and state separately.
  5. Inspect match evidence, raw runtimes, and per-query errors.

Interpret the state

A result says runtime_presence=present and agent_state=ready. What is justified?

Reveal answer and reasoning

Answer C. Presence proves a matching runtime was observed; ready means its agent can accept input. Neither claim establishes overall workspace health or completion.
